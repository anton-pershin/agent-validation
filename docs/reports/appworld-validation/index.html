Inside appworld_worker.py --evaluate-task

The language model produces the trajectory. It does not grade that trajectory. For fixed pinned AppWorld code/data and a fixed saved final state plus recorded answer, the evaluator runs deterministic Python and database assertions. The service never calls an LLM to decide pass/fail.

  1. 1Freeze the episodePublic execution has closed. AppWorld has saved database state after each world.execute call.
  2. 2Load task + versionsTask.load(task_id) loads private task data, checks DB compatibility, and fixes the task’s evaluation datetime.
  3. 3Compare start and end stateAppWorld loads the initial and final ModelCollection objects from the episode’s saved databases.
  4. 4Run task-specific Python testsThe task’s evaluation module receives private/public data, models, and the recorded answer. It calls test.case(...) and test.answer(...).
  5. 5Require every assertionTestTracker.success = (pass_count == num_tests). Failed assertions and traces go into a private report.
  6. 6Return evidenceThe parent service combines evaluator success with protocol and AppWorld completion, then retains the result/report in benchmark.json.

State task · Venmo / Phone examples

Database and collateral checks

Task-specific assertions inspect final rows, relationships, messages, likes, and unintended model changes. The API sequence can differ; the required final state must be correct.

test.case(observed_state_condition, "==", expected_condition)

What can still vary? Model sampling can produce different trajectories and final states across repeats. Once a final state and recorded answer are fixed, this verification procedure does not ask an LLM whether they look acceptable. An evaluator crash is an infrastructure failure; the service does not replace it with LLM judging.

Presentation

validation_cli.py, validation_cli_partial.py, and the HTTP API expose profile discovery, full validation, and partial validation. Full runs reject inline changes.

Execution

The orchestrator resolves configuration, checks out the exact solution revision, plans episodes, and starts isolated solution and benchmark processes.

Evaluation & evidence

Episode records feed the existing VM1–VM10 and AC1–AC7 calculators. Immutable run directories retain configuration, provenance, metrics, logs, and benchmark evidence.

The API is deterministic and stateful: reads expose public records, while writes change app databases. Agents can use apis functional calls or requester HTTP-style calls.

Exposure boundary

Included

Public instruction, supervisor fields, app descriptions, API documentation, public execution output, configured instructions, and tool schemas.

Agent computes

Actions, code, final answer, confidence, likely_incorrect, and reason. These are the agent’s own claims, not a correctness verdict.

Never included

Ground truth, answers, reference solutions, evaluation code/results/reports, repeat number, validation condition, or a goal-achieved signal.

DISCOVERY IS PART OF THE TASKNo task-specific API list is supplied in the prompt

How can the agent find apis.venmo.show_social_feed?

The protocol’s tools array contains only the generic execute_code tool. It does not contain all 457 AppWorld APIs and does not name a required API for the current task. The task does include public app descriptions, and the profile instructions tell the agent to use the public API Docs helper.

  1. 1Read the wordsThe instruction itself says “venmo transactions” and “venmo social feed.” The agent uses language understanding to form candidate app and concept names.
  2. 2Inspect public app descriptionsapp_descriptions identifies Venmo and the API Docs helper. No private required-app or required-API field is present.
  3. 3Search or list public APIsThe agent can call show_api_descriptions(app_name="venmo") or search_api_docs(query="venmo social feed transactions").
  4. 4Match description, then inspect schemaA candidate named show_social_feed has the public description “Show your social feed (transactions of your friends).” The agent can call show_api_doc for parameters and responses.
# Public discovery calls available inside execute_code:
apis.api_docs.show_api_descriptions(app_name="venmo")
# → public [{name: "show_social_feed", description: "Show your social feed ..."}, ...]

apis.api_docs.show_api_doc(app_name="venmo", api_name="show_social_feed")
# → public GET /venmo/social_feed schema

feed = apis.venmo.show_social_feed(access_token=token)
# → public transaction records

This is not an oracle. The agent must infer relevance, explore, and recover from poor choices. It can select the wrong API or fail to discover a useful one. Neither a hidden required-API list nor a reference plan is sent to it.

04 · Landlock, simply explained

A filesystem guest list enforced by the Linux kernel

Landlock is a Linux security feature. A process gives the kernel a list of paths it may read, write, or execute. Every other path is denied. It is not a container, a virtual machine, or a prompt instruction.

Kernel-enforced

Not just “please do not read this”

Even if agent code calls Path(...).read_text(), Linux returns PermissionError when the path is not on the allowlist.

One-way restriction

The worker cannot loosen it later

After PR_SET_NO_NEW_PRIVS and the Landlock rules are applied, that process cannot remove the boundary. This is why private evaluation needs another process.

Small and local

No container is required

The pinned Python runtime stays in place. Landlock adds kernel checks without a second operating system, Docker image, or persistent sandbox service.

Public task inputs are on the allowlist. The worker may read them to operate AppWorld.

The worker’s actual allowlist

The list grants only what the current episode needs. There is no rule for data/ as a whole, because that would include ground truth.

Python runtime + standard libraries
└─ read / execute allowed

data/
├─ api_docs/                 → read allowed
├─ base_dbs/                 → read allowed
├─ datasets/                 → read allowed
└─ tasks/<current-task>/
   ├─ specs.json             → read allowed
   ├─ dbs/                   → read allowed
   └─ ground_truth/          → DENIED

experiments/outputs/<episode>/
└─ read / write allowed      → saved public state

Everything else, including other episodes
└─ DENIED by default

Startup self-test: fail closed

  1. Create the world with load_ground_truth=False. No private file is intentionally opened.
  2. Apply the path allowlist and PR_SET_NO_NEW_PRIVS. The restriction cannot be lifted in this process.
  3. Try to open the current task’s ground_truth/ directory. The expected result is PermissionError.
  4. If the open succeeds, stop the episode as an infrastructure failure. Validation never falls back to AppWorld’s ordinary guards alone.

This test matters because a normal AppWorld Path.read_text() call can otherwise read ground truth. Landlock closes that concrete gap.

🐍 Public execution worker

  • Runs agent code with public AppWorld data.
  • Cannot read ground truth or unrelated host paths.
  • Receives no provider or provisioning credentials.
  • Reports AppWorld completion and closes before evaluation.

🔐 Separate trusted evaluator

  • Starts only after a valid protocol completion declaration.
  • Runs no agent code and receives only the saved episode state.
  • Reads private ground truth and task-specific programmatic tests.
  • Returns a private result/report for evidence; the solution sees neither.

From one episode to acceptance criteria

Landlock protects confidentiality; it does not decide task correctness. Correctness still comes from the protocol completion declaration, AppWorld task completion, and the independent evaluator.

05 · Evidence and resources

Frugal by default, configurable by design

Memory depends on active workers, not the 630-episode total. The default is one worker, while profile and service-wide concurrency settings remain configurable for larger machines.

Measured no-op baseline
659–660 MiB

Peak RSS for one real AppWorld worker across probes from train, dev, and test_normal.

Illustrative scale: 3 GiB host hard limit, not expected use and not an upper bound for agent code.

Operational evidence
  • About 7.1 CPU-seconds per fresh no-op worker lifecycle
  • Configured and actual package/data versions in evidence
  • Landlock ABI and execution/evaluator resource observations
  • Private evaluation result and report retained outside the solution protocol
  • Partial startup and abort paths preserve available diagnostics
  • Temporary experiment output is removed after evidence is retained

What to remember

Full

630 episodes at concurrency one have a 52.5-hour maximum episode-time budget at 300 seconds each. Model latency dominates real runs.

Partial

Iterate on one task or any subset. Keep at least two repeats for AC3, or remove AC3 from a one-repeat diagnostic run.

Scale

Increase episode_concurrency and service-wide capacity only after measuring real solution memory and CPU on the target host.
